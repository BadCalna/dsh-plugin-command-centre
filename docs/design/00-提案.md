# 任务指挥台（Mission Control）— 提案 v0.1

> 综合三份调研：`panel-api.md`（渲染面可行性）、`data-signals.md`（数据可达性）、`concepts.md`（三种范式）。
> 结论：**能做，而且比想象的便宜**。核心难点不在界面，在「产出」这一列的数据定义。

---

## 1. 需求翻译

你说的三件事，翻译成设计语言就是三个诉求：

| 你说的 | 真实诉求 |
|---|---|
| 看到各个对话的产出和进度 | **同时可见性**：一屏内比较 N 个任务，而不是一个一个点开 |
| 看到 subagent 的创建、处理、和主 agent 的关系 | **拓扑可见性**：谁在替谁干活、卡在哪一层 |
| 区别于 codex 三栏 | **组织维度要换**：三栏的单位是「对话」，你要的单位是「任务/运行单元」 |

三栏真正坏的地方不是"三列"，而是：左列只回答"有哪些对话"（不回答状态），中列一次只能看一个（不回答并发），右列和进度无关（断开了）。所以解法不是"换一种三列"，而是**换一个观察单位**，并让"异常"强制浮到最上层。

---

## 2. 三个硬约束（已核实，决定方案边界）

1. **插件拿到的"整页"只是中列。** `main` 是 shell 的中列出口；左列（会话树）、右列（详情/输出）属于 shell，插件碰不到。要真正替换整个窗口只能 shadow `root` —— 那会顶掉整个宿主 UI，升级必碎，不做。
   → **这反而合适**：你保留了熟悉的左侧导航，只把"中间那块地"变成指挥台。
2. **入口 = `main` 的一个新 key + `sidebar.panellist` 的同名字典。** 已验证，先例是「插件」页和「自动化任务」页。全新 key/id 是**纯增量**、可卸载、与对话面板共存。选中态不持久化（刷新回对话），这一点要接受。
3. **数据 90% 现成。** Client 侧已有 `useSessions`（全部会话 + `parentId` + 每个会话的投影值）、`useSessionStatus`（running/idle）、以及现成投影：`subagentCatalog`（子 agent 目录）、`subagentTiming`、`agentTeam`（团队+共享任务）、`goal`、`plan`、`todos`、`tokenUsage`、`contextPressure`。
   → **不写一行 Host 代码，就能做出"状态 + 进度 + 关系"三层。** 缺的只有"产出文本/最后工具/workflow 摘要/子 agent 结束原因"，这四项共用一个 Host 投影（阶段 2）。

---

## 3. 我的设计立场

**默认视图 = 分组矩阵 + 行列内嵌子树；点开 = 详情抽屉。**
（即 concepts.md 的范式 C 做骨架、A 做默认展开；B「交付码头」留作第二 tab，等"产出"定义清楚再上。）

为什么不是以树为主页：真实使用里 subagent 关系很浅（1 主 + 1–6 子），做成主页等于为一个二级问题牺牲全局视野；而且 10 个并发任务时树会退化成带缩进的列表。

两处对 concept 稿的修正：
- **第一层子 agent 默认展开**，不藏在 `space` 里 —— 因为"关系"是你的核心诉求，默认就该看得见；>3 个子时收成 `+N`。
- **异常不是"高亮一行"，而是接管顶部横幅**。三栏最大的病是"审批埋在对话里等你想起来"，这里要变成"不处理它就一直在最上面"。

三个范式各自的定位：**矩阵是首页（triage），树是行内放大镜（关系），交付码头是第二 tab（验收）**。三层共用同一套数据与键盘习惯，不做成三个产品。

## 5. 范围切分

| 版本 | 内容 | 依赖 | 预估 |
|---|---|---|---|
| **V1a** | 整页 + 入口图标；分组行（需要你/运行/空闲/失败）；状态点、代理链、todos 进度、上下文压力、时长；第一层子树默认展开；详情抽屉；点行打开对话；键盘 | **纯 Client，0 行 Host** | 小 |
| **V1b** | 「产出」列与抽屉产出区（最后回复摘要 / 最后工具 / 改动文件 / 子 agent 结束原因） | 1 个 Host 投影 `missionControl` | 中 |
| **V2** | 顶部横幅可直接批准/回答（可写控制台）；「交付码头」tab；workflow 阶段与团队任务的专门展示 | 需要动作通道 + 产出模型 | 中 |
| **V3** | 历史流水/回放、goal 与定时任务整合、窄屏降级、记住上次面板 | — | 大 |

**明确不做**：替换左/右列（shadow shell）；iframe 独立页面；require 宿主 Client 包；为每个会话开 history 流。

可选加分项（都是纯增量、低风险）：
- 在对话页加一个 **「任务」View 标签**（`conversation.view`）——看单个对话时也能看它的 subagent 树。
- 在右侧栏加一个 **「产出」页签**（`sidebar.right.pane.tab`）。
> 我的建议：**先不做**。V1 先证明"整页指挥台有人用"，再加这两处，否则会同时长出三个入口。

## 6. 风险

1. **Client inspect 本轮多次超时**：live slot 契约靠 0.2.1-rc.3 源码 + 内置契约目录交叉验证，字段名可能有极小偏差 → 落地时以真插件跑通为准。
2. **面板选中态不持久**：刷新/重启回对话页。若你要求"打开就进指挥台"，只能在加载时调 `selectPanel`（时序未验证，且会打乱"新会话"习惯）。
3. **新增 Host 投影会广播给所有 Client**（每次重连的 baseline）→ 只放小 JSON（截断文本、计数、枚举），不要放 diff/长文本。
4. **"产出"没有现成模型**：这是全案唯一真风险，见 Q2。
5. **异常状态色常驻**会视觉疲劳，需要"安静模式"（降饱和、只用左侧竖条）。
