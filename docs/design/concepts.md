# Mission Control：三种「非三栏」界面范式（设计探索稿）

> **对象**：DeepSeek Harness Web UI 的插件页，渲染在中央 main panel，按 1200–1600px 宽设计。
> **性质**：讨论稿，不是视觉稿。线框里的 `[R]`、`#`、`|-` 是占位符，实际实现用状态色、图标、动效。
> **建议读法**：先看 §0（出发点）和 §6（推荐 + 待拍板），再按兴趣看 §2–§4。线框按 96 个等宽字符宽绘制，约等于 1200–1600px 的一屏。
> **本文标注**：`[假设]` = 尚未验证或需要你确认的前提；§6.3 是需要你拍板的 5 个问题。

## 0. 出发点：三栏坏在「组织维度」，不是布局

codex 式三栏（左对话列表 / 中对话详情 / 右输出）隐含一个前提：**你同时只关心一段对话，而且所有答案都在这段对话里**。重度并行使用时，这个前提在三处失效：

1. **并行不可扩展**：列表只能说明「有 20 个会话」，说不出哪个在跑、跑到第几步、哪个卡住。只能逐个点进去确认。
2. **关系不可见**：subagent 在对话里只是若干条工具消息加一次返回。谁是父、在替谁做什么、哪些已回收，要重读文本才能还原。
3. **产出不可见**：产物散在各自对话末尾或文件系统里，没有「我现在该验收什么」的统一入口。

所以下面三个范式不是三种皮肤，它们各自替换一个维度：

| 范式 | 替换的维度 | 一等公民 | 一句话 |
|---|---|---|---|
| **A 任务树** | 列表 + 详情 | 委托关系 | 一屏看几棵树：谁在替谁干活 |
| **B 交付码头** | 右侧输出面板 | 产出物 | 不问过程，只问今天交了什么 |
| **C 指挥矩阵** | 左侧会话列表 | 并行单元 | 一行一个任务，像塔台的航班条 |

> 三者共用数据源，但对同一份数据的取舍不同 —— 这正是需要拍板的地方。

## 1. 三个范式共用的基础约定

### 1.1 状态语言（全篇一致）

`[R]` 运行中 · `[?]` 等你输入 · `[!]` 等你决策或审批 · `[.]` 完成 · `[X]` 失败 · `[-]` 空闲。

- 时间一律用「多久之前 / 还要多久」，绝对时间只出现在详情里。
- 进度条 `[####----]` 一律表示**当前单元内部的步数完成度**，不表示时间，也不跨单元比较。
- 状态色只用于状态字与左侧 2px 竖条，不整行染色（否则一屏都是颜色，反而看不出异常）。

### 1.2 什么算「一个任务单元」

不先定义这个，三个范式都会算错数。

- **默认**：一个顶层对话 = 一个单元。
- **workflow run**：并入它的父对话，在单元内显示 `wf(3)`；没有父对话时独立成单元。
- **Agent Teams**：一个团队 = 一个单元，成员和共享任务在单元内展开（团队不是对话，不该混进会话列表）。
- **subagent**：不是单元，是单元内部的节点 —— A 的枝条、C 展开后的子行、B 卡片来源链上的一环。
- **[假设]** 一个对话只有一条主 agent 链；如果 shell 允许多条并行输入，单元定义要改成「一次 turn」。

### 1.3 三条设计原则

1. **注意力优先**：需要你处理的永远最先出现且可预期（A 置顶 / B 最左列 / C 顶部横幅），不靠你自己巡视发现。
2. **关系画出来，但默认折叠**：拓扑是第二层信息，展开即见，不占首屏。
3. **产出必须可溯源**：任何一张产出卡都能两步内回到「哪个会话、哪个 agent、哪一步」。

## 2. 范式 A：任务树 Mission Tree

### A-0 立意

> **把「谁委托谁」当成一等公民。** 每个对话是一棵树：主 agent 是树干，subagent 是枝条，产出是挂在枝上的结果。首屏是几棵并排的树，而不是一段对话。

视觉主体是缩进 + 连线 + 状态。一个任务的全部结构（主 → sub → 工具 → 产出）在一屏里可读，不需要进对话读消息流。

**为什么是树，不是放射/星系图**：树天然有方向（谁委托谁）、有层级、可键盘上下扫读，标签有固定的位置。放射图在 8+ 节点时连线交叉、中文标签互相抢空间；而真实的 subagent 数常常到 4–6，正是放射开始不好用的区间。视觉上的"炫"在这里是负资产。

### A-5 信息层级

- **常驻**：每个单元的根行 —— 任务名 / 当前步 / 状态 / 耗时 / 产出数 / 主操作；顶部状态计数；「需要你」置顶区。
- **自动展开一层**：`[R]`、`[!]`、`[?]` 的单元默认露出最近一个 subagent 及其任务名；已完成单元收成一行。
- **按需（Enter / 点击）**：右侧抽屉（约 420px 浮层，不占常驻列）显示节点详情 —— 原始指令、工具序列、产出清单、耗时、token；抽屉内可跳会话。
- **折叠策略**：subagent 超过 3 个只显示前 3 + `+N`；已回收 sub 只保留一行结果摘要；工具调用默认不出现，只在抽屉里。
- **空状态**：见 A-4。要点是保留「教学骨架」，第一次打开就知道这页长什么样、能干什么。

### A-6 用这个范式怎么回答四个问题

1. **哪些任务在跑？** 根行状态标记 + 顶部计数；排序固定为 需要你 > 运行中 > 最近完成，所以你永远先看到要动的和正在动的，不需要自己找。
2. **每个产出了什么？** 根行有「产出 N」；展开后产出以结果节点挂在对应枝上（文件名 / 结论摘要），`[看产物]` 直接进抽屉，不用打开对话翻消息。
3. **subagent 在替谁干什么、卡在哪？** 树的强项：缩进就是层级，枝上写任务名，右列写当前动作/工具；`[!]`/`[?]` 标在枝上并附一句原因（「等你批准删表」「问：e2e 还是单元」）。回收的 sub 保留结果摘要，方便回看它交了什么。
4. **我下一步点哪里？** 最顶「需要你」区就是答案：一行一个待办，行内就是动作按钮；按 `!` 直达最急。没有待办时，运行中单元的「下一步」行给出建议动作（如「合并 3 个结果 > 跑 e2e」）。

### A-7 交互细节

- **键盘**：`j/k` 上下、`h/l` 或 `space` 折叠展开、`Enter` 进入（会话或子 agent 抽屉）、`o` 在对话面板打开、`!` 跳最急、`/` 搜索、`f` 只看需我、`g/G` 首尾。
- **悬停**：节点 tooltip 显示最近 3 条事件、完整委托描述、token 用量。
- **点击**：根 = 打开该会话面板；sub 节点 = 打开抽屉（抽屉里有「在对话中查看」）；产出节点 = 打开产物（文件预览 / 下载）。
- **跳转与返回**：从树跳进对话后，返回按钮回到树并保留滚动位置与展开状态。若 shell 不允许插件面板与对话面板共存，则用抽屉承载「轻查看」，把真跳转留给明确的 `o`。**[假设]** shell 支持面板切换与返回栈。

### A-8 代价与弱点

- **缩进吃宽度**：每层 4 个字符，三层后任务名只剩约 20 个显示字符，长标题会被截断。
- **并行天花板低**：10 个并行任务时首屏只能放 3–4 棵树，其余的要么滚动、要么折叠成一行；树会退化成「带缩进的列表」。这是 A 不作为首页的主要原因。
- **折叠即丢信息**：折叠后只剩计数 ——「我知道有 3 个 sub 在跑」但不知道在干什么。
- **空状态和浅任务时显得空**：大部分时间树只有根 + 一句当前步，视觉上像没做完。
- **学习成本中等**：折叠规则、置顶规则要解释一次；`[!]` 置顶会打乱「按时间」的心理模型，有人不适应。

### A-9 与 shell 的契合

**整页替代 main 面板**，侧栏只多一个图标；不做对话面板旁的附加栏，也不复制会话列表 —— 树不是会话列表，是关系图。与对话面板互斥切换，但保留返回路径。对现有 sidebar 的态度：只借它作为入口，不改它的结构、不往它里面塞会话。

## 3. 范式 B：交付码头 Delivery Dock

### B-0 立意

> **把「产出物」当一等公民。** 界面不问「你在跟哪个对话」，只问「今天有哪些东西被做出来了、哪些等我验收」。三列就是流程的三个状态：待你处理 / 进行中（半成品）/ 已交付。

**为什么不是收件箱列表**：验收是有状态的（待处理 / 已交付 / 卡住），而且「半成品」必须可见 —— 纯列表无法表达「还在长」。三列 + 卡片能同时给出状态和内容。

**[假设] 产出的定义**：暂按「文件写入 / 报告文本 / diff / 明确结论」识别。这依赖数据层能力或 agent 显式声明，是三个范式里技术风险最大的一处（见 Q3）。

### B-5 信息层级

- **常驻**：三列 —— 待你处理（最左）、进行中（半成品 + 进度 + 当前 step）、已交付（按天分组）。每张卡：标题、类型、来源链、时间、主动作。
- **折叠**：已交付默认只显示标题 + 时间；来源链超过两段折叠成 `+N`；同一任务的多个版本折叠成一张卡（角标 `v3`），点开才是版本列表。
- **按需**：点卡片在底部展开「验收托盘」（预览 + 来源 + 备注 + 验收/打回），不新开页面；打回必须写理由。
- **空状态**：见 B-4。重点是给出「产出」的定义和昨天历史的入口。

### B-6 用这个范式怎么回答四个问题

1. **哪些任务在跑？** 进行中列 + 顶部「生产线上游」条（列出活跃生产者）。**盲区**：不产出东西的任务（纯调研、纯对话）不会出现在这里 —— 顶部条只能缓解，本质上 B 是「产出优先」，不是「任务优先」。
2. **每个产出了什么？** 这就是界面本身。可按类型 / 来源 / 时间筛选；已交付可追溯来源。
3. **subagent 在替谁干什么、卡在哪？** 卡片来源链（父任务 > main > sub）+ 半成品卡的「正在: sub:xxx」+ sub 的中间产物提前以半成品出现。但**不做全局拓扑**：「一个 sub 挂了会影响谁」看不出来，需要点进来源。
4. **我下一步点哪里？** 最左列 + `a` 验收 / `r` 打回 / `Tab` 下一件；卡住项在底部单独一条横条。验收是唯一需要你「做决定」的地方，所以它被放到最左、最亮。

### B-7 交互细节

- **键盘**：`j/k` 选卡、`Tab` 切列、`Enter` 预览、`space` 展开托盘、`a` 验收、`r` 打回（必须填理由）、`o` 打开来源会话、`/` 搜索、`g` 切列。
- **悬停**：卡片浮出「来源摘要」：哪个会话、哪些 agent 参与、耗时。
- **点击**：卡片 = 展开托盘；来源 chip = 跳会话并定位到产出消息；sub chip = 打开 sub 抽屉；版本角标 = 展开版本列表。
- **不做拖拽**：验收是决策动作，拖拽容易误操作，且把「状态」和「位置」耦合成同一个手势。

### B-8 代价与弱点

- **依赖「产出」的定义**（最大风险）：识别不准就会漏卡或噪声爆炸。纯聊天/调研类任务的产出最难识别。
- **版本爆炸**：迭代会产生 v1…v7，需要版本折叠，否则一天就刷屏。
- **无产出任务会隐形**：和「我要看清所有」的诉求直接冲突，这是 B 不能做首页的根本原因。
- **低频入口**：验收一天可能只有几次；如果用户习惯「边聊边看」，B 会变成第二入口。
- **卡片内信息比对话少**：想深挖必须跳走，不能「在面板里读完」。
- **容量**：适合 5–20 件/天的量级；50+ 件需要搜索、归档和按来源折叠。

### B-9 与 shell 的契合

**整页 tab**，与 C 并列（同一个插件的两个视图），侧栏一个入口。不替代对话，也不试图覆盖「读对话」的场景 —— 它只负责「交收」。对 sidebar 的态度：与 A 相同，只借入口。

## 4. 范式 C：指挥矩阵 Mission Matrix

### C-0 立意

> **一屏就是一张表；单位不是对话，是「正在运行的单元」。** 像 htop、像塔台的航班条：谁在跑、哪一步、产出什么、卡多久，一行一个；异常的强制置顶。

**信息密度是首要目标**，其次是可操作性。**为什么不是卡片瀑布**：卡片占空间，10 个单元就要滚动；矩阵一屏 18 行，靠列对齐实现「横着比较」—— 这是「一眼看清 N 个」唯一可靠的做法。

### C-5 信息层级

- **常驻**：每行七个字段（编号 / 任务 / 代理链 / 当前步 / 进度 / 最新产出 / 时长）；顶部「需要你」横幅；右上视图切换（活跃 / 全部）。
- **折叠**：默认 18 行/屏 + 分组（需要你 / 运行 / 空闲 / 完成）；subagent 压成 `main+3s`；已完成收进组尾；`...` 表示还有更多。
- **按需**：`space` 行内展开子树（内联、不换页）；`Enter` 右侧抽屉（约 420px 浮层）看详情；`o` 跳对话。
- **空状态**：见 C-4，保留空行骨架 + 下一步建议（新建 / 打开对话 / 定时任务）。

### C-6 用这个范式怎么回答四个问题

1. **哪些任务在跑？** 行 + 分组 + 计数；排序 = 需要你 > 失败 > 运行 > 空闲。横着扫一遍就知道「有几个、分别在哪一步」。
2. **每个产出了什么？** 「最新产出」列（文件名 / 条数），展开或抽屉里看清单。产出列只放"最新一件"，历史在抽屉。
3. **subagent 在替谁干什么、卡在哪？** 代理链列（`main+3s`）一眼看出并行度，`space` 展开看具体任务、工具、是否阻塞；「卡在哪」在操作列（`!`/`?`/`r`）和顶部横幅里。
4. **我下一步点哪里？** 顶部横幅内联动作 + 行末操作标记 + `!` 跳最急；`Enter` 抽屉里做决定。这是三个范式里「从看到到动手」路径最短的。

### C-7 交互细节

- **键盘**：`j/k` 移动、`Enter` 抽屉、`space` 展开子树、`o` 打开对话、`1-9` 跳行、`/` 过滤、`f` 只看活跃、`g` 切分组、`!` 最急、`?` 帮助。
- **悬停**：行浮出最近 3 条事件、token/费用、最后一次工具调用。
- **点击**：行 = 抽屉；任务名 = 抽屉；`> ` 处点击 = 展开；列头点击 = 排序。
- **跳转路径**：行 → 抽屉 → `o` → 真实对话；sub → 抽屉内的 sub 页签（含「在对话中查看」）。所有跳转都保留矩阵的滚动位置与选中行。

### C-8 代价与弱点

- **列宽紧张**：中文标题到第 16 个显示字符就被截断，长任务名只能靠 tooltip。
- **学习成本最高**：第一次看会像「监控大屏」，需要 5–10 分钟适应。若不熟悉键盘，收益减半。
- **窄屏会崩**：<1200px 需要降级为两列（任务 + 状态），信息丢一半。
- **语义歧义风险**：进度条是步数还是时间、`main+3s` 是否包含已回收的 sub，都必须在图例里写死；否则会误读。
- **20+ 单元靠筛选，不靠滚动**；但它对「阅读型」用户不友好 —— 它不给你叙事。
- **视觉疲劳**：常驻高对比状态色，长时间盯会累，需要「安静模式」（降饱和、只用左侧竖条）。

### C-9 与 shell 的契合

**整页替代 main**，侧栏一个图标。可选叠加模式 V2：在对话面板顶部嵌一条 4 行高的只读矩阵带（点击行跳转），但那需要 shell 允许插件往 conversation 面板注内容，且很容易长成「新的三栏」。**默认不做**，保持「整页切换」。对 sidebar 的态度：只借入口，不新增第二层导航。

## 5. 同一份数据，三种落点

| 数据信号 | A 任务树 | B 交付码头 | C 指挥矩阵 |
|---|---|---|---|

| turn / step 进度 | 「第 n/m 步」+ 耗时 | 半成品卡进度条 | 当前步列 + 进度条 |
| 工具调用 | 展开枝上的「read x6」 | 「正在: xxx」 | 展开行「read x6」 |
| subagent 父子 / 状态 | **缩进枝条（视觉主体）** | 来源链一行 + 贡献者 | 代理链 `main+3s`，`space` 展开 |
| Agent Teams | 一个团队 = 一棵树 / 一个大枝 | 卡片「多人协作」标记 | 行内 team 标记 + 展开成员 |
| workflow 阶段 | 枝内 phase 进度 | 卡片的阶段名 | 当前步 `wf(3)` |
| goal | 置顶 root 条 | 卡片「目标」标签 | 顶部细条 |
| schedule | 树底「下次 14:00」 | 无 | 底栏「下次 14:00」 |
| 文件改动 | 产出节点（文件名） | **卡片主体（文件 / diff）** | 最新产出列 |

| token / 费用 | 抽屉 | 卡片角标 | 行 hover |

## 6. 推荐与分歧点

### 6.1 我的推荐：C 做首页，A 做展开，B 做第二 tab

不是三选一，而是三层深度：

- **V1 打开插件 = C（指挥矩阵）**，矩阵每行 `space` 内联展开成 A 的子树。也就是说 **A 不是另一个页面，而是 C 的放大镜** —— 关系视图在需要时才长出来。
- **B 放在第二个 tab**（或侧栏第二个入口），承担「验收 / 收尾」这个低频但关键的动作。
- 三范式共享同一套数据与键盘习惯，避免变成三个产品。

**为什么是这个优先级**

1. 第一诉求是 triage（谁在跑 / 哪卡住 / 产出在哪），triage 的答案取决于**同屏能比较多少单元**和**是否强制排序** —— C 两项都最强。
2. subagent 关系在真实使用里通常是浅的（1 主 + 1–6 sub），「行内展开」就够；把它做成首页，等于为一个二级问题牺牲全局视野。
3. B 的价值最高，但依赖一个目前不存在的「产出模型」，技术风险最大，所以放第二。
4. 你自己也还没定形式 → 先给最不容易错的「全局视图」，把「关系」和「产出」做成可展开的层，而不是三个平权的产品。

**不建议**：三个并列 tab 平权（要学三套扫描方式，且首屏不知道该看哪个）；也不建议先做 A 首页（好看，但并行天花板低，10 个任务就退化）。

### 6.2 建议的落地顺序

1. **V1**：C 只读 + 跳转 —— 行、分组、顶部横幅、只读抽屉、`o` 跳对话。
2. **V1.5**：C 行内展开子树（= A 的核心）+ 顶部动作（批准 / 回答 / 重试）。
3. **V2**：B tab + 产出模型（先定 Q3）；workflow / team 的专门展示。

### 6.3 必须由你拍板的 5 个问题

**Q1. 首页是谁，以及入口形态？**
- 选项：① C 矩阵（推荐）② A 树 ③ B 码头 ④ 三者并列 tab（默认 C）。
- 追加选项：是否允许它成为**打开 Harness 就看到的默认页**（会改 shell 默认行为），还是必须点侧栏图标才进入。
- 影响：首屏回答什么问题、插件先做什么、是否要动 shell 默认行为。

**Q2. 只读监控台，还是可写控制台？**
- 选项：① 只读 + 跳转（推荐 V1）② 可写：审批 / 回答 / 中止 / 重试 / 新建任务。
- 影响：工作量约 1.5–2 倍；误操作风险；插件需要的权限。但「下一步点哪里」只有可写才真正闭环。

**Q3. 什么算「产出」？（B 成败的关键）**
- 选项：① agent 显式声明（新增工具/字段，最准，但要改 agent 约定）② 由文件写入推导（无需约定，纯研究任务会漏）③ 最终回答也算产出（覆盖广、噪声大）④ 手动钉选兜底。
- 影响：B 的卡片是否可信、数据层工作量。我的倾向：②+③ 打底，允许 ④ 修正。

**Q4. subagent 能不能被独立进入？**
- 选项：① 能（有自己的 transcript 视图）② 只能从父任务展开，抽屉只读 ③ 完全不能进入，只能跳父对话。
- 影响：A 的跳转路径、A 的核心价值、shell 是否暴露 subagent transcript（**未验证**）。

**Q5. 时间维度：只看当下，还是要历史？**
- 选项：① 只看当下（推荐 V1）② 加「今日流水」（按天分组）③ 完整历史 + 检索。
- 影响：布局（C 的时间列 / 日期切换）、存储成本、B 的归档策略。
